Step 3 of 11 · The pivot

Turn retrieval into a tool

You write this

This is the moment your bot stops being basic RAG. Until now you called the search. Now you wrap it in @tool and hand it to the model — and the model decides whether to use it.

Read that docstring carefully. It is not a comment. @tool hands it to the model as the tool's description, and it is the entire basis on which the model decides to call this or not. It is the sign on the shop door.

LangGraph does this for you
  • Reads your function signature and builds a tool schema from it.
  • Hands your docstring to the model as the description.
  • Runs the function when the model asks — and only then.
  • Wraps whatever you return into a tool message on the conversation.

Watch out — The tool does not run every turn

This is the number one misunderstanding. Adding a tool does not mean it fires on every question — it fires when the model asks for it. Type "hello" and it should never run. If it does, your docstring is too broad.

Your turn — in your client's bot

This is the most important edit you will make. Two parts:

  • Rename the function for your client's domain — search_festival_rules.
  • Rewrite the docstring to name the subjects your bot actually covers: "…any question about passes, entry, age limits, refunds, or venue rules."

Find this in your AI Agent Organisation. In the workbook you named an agent whose job was to look things up — the Ava of your crew. This tool is that agent. Its ONE JOB from your org chart is exactly what belongs in this docstring. If you wrote the boundary well in the workbook, you can almost paste it in.

Step 5 of 11 · Node 2

Grade what came back

You write this

A vector search always returns something. Ask for the top 3 and you get 3, even when all three are useless. It is the fish stall — the vendor hands you the three nearest fish in the box, and nearest is not the same as right. You look before you pay.

Notice what this returns: not data, but the name of the next node. That is what makes it a routing function.

LangGraph does this for you
  • Reads your returned string and jumps to the node with that name.
  • with_structured_output forces the model into your shape — you never parse text.
  • Keeps the full conversation intact across the jump.

Watch out — Node functions and routing functions are different animals

A node function returns state: return {"messages": [...]}. A routing function returns a node name: return "generate_answer". Mixing them up is the error you will hit most often, and the traceback rarely says so plainly.

The four mistakes everyone makes

1 · Expecting the tool to run every time

It runs when the model asks. If a greeting triggers a search, fix the docstring, not the wiring.

2 · Mixing up node functions and routing functions

Nodes return state: return {"messages": [...]}. Routers return a node name: return "generate_answer". Hold that pattern and half your errors vanish.

3 · Forgetting compile()

workflow is the blueprint; graph is the built thing. You invoke the graph.

4 · Leaving the loop uncapped

The one that costs money. Add a counter to the state, stop at three, answer honestly with what you have.

MAX_RETRIES = 3


def grade_documents_with_limit(state) -> str:
    if state.get("retry_count", 0) >= MAX_RETRIES:
        return "generate_answer"     # give up gracefully, and say what you don't know
    # ... the usual grading ...


def rewrite_question_with_counter(state):
    result = rewrite_question(state)
    result["retry_count"] = state.get("retry_count", 0) + 1
    return result

Taking this to your client bot

  1. Swap the four starter rules for your client's real documents — the code does not change, only what you upsert.
  2. Rewrite the tool docstring in your client's language. This is the highest-leverage line in the file.
  3. Test with three questions of your own: one greeting, one factual, one deliberately vague.
  4. Add the retry cap before you demo it to anyone.
  5. Check it says "I don't have that" when the documents genuinely do not cover something.
